# Sentinel Security Journal 🛡️

## 2026-07-24 - Outbound Links Reverse Tabnabbing and Referer Information Leakage
**Vulnerability:** Outbound links with `target="_blank"` were using `rel="noopener"`, which lacks `noreferrer`. This could allow the destination website to receive the `Referer` header (containing details about the application URL, self-hosted endpoints, or workspace paths) and could potentially leak context information. In addition, the modern standard is to consistently use `rel="noopener noreferrer"` for external anchors to prevent reverse tabnabbing.
**Learning:** Modern web browsers require explicit security attributes for outbound links. Single-page client-side applications containing user API keys or workspace integrations must be especially careful not to leak the referrer URL when users click internal settings links, help documentation, or repository branches.
**Prevention:** Always include `rel="noopener noreferrer"` on all anchors pointing to external domains using `target="_blank"`.

## 2026-07-25 - Client-Side API Connection Pool Exhaustion & Denial of Service
**Vulnerability:** Outbound HTTP request functions (`apiCall`) lacked explicit timeouts. Under conditions where remote API endpoints or intermediate network routes hang indefinitely or respond very slowly, pending fetches could block client-side resources indefinitely. In polling-heavy SPAs, this causes promise accumulation, browser connection socket limit exhaustion (connection pool lockup), and client-side memory leakage, leading to UI lockups/Denial of Service.
**Learning:** Polling and synchronization tasks in client-side applications must be bounded by defensive timeouts. Relying on default browser connection timeouts is insufficient, as some requests may remain open for minutes or indefinitely, causing socket limits to be reached quickly.
**Prevention:** Always implement explicit, bounded request timeouts using `AbortController` in client-side fetch abstractions to ensure connections are freed under hanging or slow network states.

## 2026-07-26 - LocalStorage Quota Exhaustion & Browser Performance Denial of Service (DoS)
**Vulnerability:** Client-side input fields, textareas, and search queries (such as session prompt inputs, follow-up messages, search filters, and feedback fields) lacked character length restrictions (`maxLength`). If a user entered or pasted an extremely large payload, the synchronous LocalStorage state persistence layer could throw a `DOMException` due to quota exhaustion (exceeding the standard 5MB browser limit), permanently breaking the client's storage mechanisms. Additionally, processing or re-rendering extremely large strings in React state triggers high memory usage and browser UI freezes.
**Learning:** All user inputs must have defensively configured maximum length boundaries at the interface level, especially in client-only single-page applications where state persistence shares a single Origin-wide LocalStorage store.
**Prevention:** Enforce strict and reasonable `maxLength` limits on all `<input>` and `<textarea>` components to prevent out-of-memory or quota-exhaustion issues.

## 2026-07-27 - Malformed API Credentials and Client-Side Cross-Site Scripting (XSS) via Dynamic URL Schemes
**Vulnerability:** First, client-side entry forms and centralized API layers allowed arbitrary structures to be accepted as API keys without validation. This allowed malformed input or injection strings to be executed, bypassing early UI failures. Second, the single-page application directly rendered dynamically matched Pull Request and Session URLs (`pr.url`, `session.url`) into anchor tag `href` attributes without validation, exposing a client-side Cross-Site Scripting (XSS) vulnerability if any URL was injected with a `javascript:` protocol scheme.
**Learning:** Defense-in-depth requires robust input validation at both the UI layer and the network wrapper layer, and dynamic external URLs rendered in interactive markup must be strictly filtered to safe protocol schemes (`http:` or `https:`).
**Prevention:** Utilize a `safeUrl` helper to sanitize all dynamically injected anchor tag links. Validation of API key format is handled at the remote API level to allow flexibility for different API key types.

## 2026-07-29 - Client-Side Runtime Compilation vs. Production Hardening Content Security Policy (CSP)
**Vulnerability:** Single-page applications utilizing inline script tag CDNs and dynamic JSX transpilers like `@babel/standalone` at runtime typically require `'unsafe-eval'` in their script-src Content Security Policy (CSP) directive. Retaining `'unsafe-eval'` in production environments creates a significant security gap, making the application susceptible to code execution exploits.
**Learning:** It is possible to balance developer productivity and security by utilizing different CSP policies for development and production. While local browser development requires runtime eval, production compilation strips out the Babel standalone engine completely and outputs a statically precompiled JSX artifact, means `'unsafe-eval'` is obsolete in production.
**Prevention:** Implement a dynamic build-time hardening process. Set the default source-level CSP to include `'unsafe-eval'` for local browser running, and configure the production build script (`build.js`) to automatically strip out `'unsafe-eval'` and development-only preconnect/CDN endpoints during packaging to enforce the strictest possible policy on the deployed site.

## 2026-08-01 - Regressed API Key Validation & Real-time Format Verification feedback
**Vulnerability:** The client-side API key validation regex in `isValidGoogleApiKey` was regressed to a dummy `/.*/` pattern, which accepted any input. This bypasses early client-side defense-in-depth, allowing malformed strings, newlines, or potential HTTP injection characters to be propagated into active request headers. Furthermore, the API key settings input did not provide visual warning feedback or prevent common paste/whitespace-entry errors.
**Learning:** Security validation functions must be strictly bounded to prevent regressions from degrading security checks. Pairing robust validation helpers like `isValidGoogleApiKey` with immediate, accessible client-side UI feedback (such as WCAG-compliant role="alert" warnings and focus-visible indicators) is critical to guide users securely and maintain credential cleanliness.
**Prevention:** Always implement a restrictive character-based match (e.g., matching printable non-space ASCII `/^[\x21-\x7E]+$/`) for API key inputs, and provide clear real-time validation states in both the connection setup screen and settings panel.

## 2026-08-02 - CSP CDN Wildcard Bypass Hardening
**Vulnerability:** Whitelisting an entire CDN origin like `https://unpkg.com` in the Content-Security-Policy (CSP) `script-src` directive introduces a bypass vulnerability because CDNs allow any user to upload arbitrary npm packages. If any HTML injection or DOM XSS occurs, attackers can load external scripts from unpkg.com, bypassing CSP entirely.
**Learning:** When using public CDNs for common libraries in production, avoid whitelisting the whole origin. Instead, restrict the CSP to the exact full file paths actually loaded.
**Prevention:** Restrict the allowed script paths in the CSP to exact files (e.g., specific React and ReactDOM URLs) during the production build script (`build.js`) to minimize the attack surface.

## 2026-08-08 - GitHub PAT Format Validation and HTTP Header Injection Mitigation
**Vulnerability:** The application accepted arbitrary strings as GitHub Personal Access Tokens (PAT) and dynamically injected them into fetch request `Authorization` headers in background API calls. This lacked validation and could potentially expose the application to HTTP Header Injection or Request Splitting if a malformed token containing newline or carriage return characters was loaded.
**Learning:** Standard security credentials must be verified on the client-side to ensure compliance with expected formats before dynamic header construction occurs.
**Prevention:** Define a defensive helper `isValidGithubToken` restricting the optional PAT to printable non-space ASCII characters (`/^[\x21-\x7E]+$/`), and pair it with accessible visual warning alerts (`role="alert"`) directly on settings inputs.

## 2026-08-09 - Duplicate Session Creation and Quota-exhaustion Denial of Service (DoS)
**Vulnerability:** Under high-latency mobile networks or slow API backends, a user clicking "Create Session" may trigger multiple consecutive POST requests to the `/sessions` endpoint if they double-click the submit button or if the connection is dropped and retried. This can result in duplicate active sessions being initialized, which drains the user's daily rolling quota (e.g. 15 sessions for free tier) and exhausts server-side resources, creating a client-side performance and quota-based Denial of Service (DoS) vulnerability.
**Learning:** For state-changing creation endpoints in client-side applications (especially those restricted by rolling daily usage quotas), it is essential to employ idempotency mechanisms. Generating a unique UUID/idempotency key on the client at the start of the creation flow and passing it both inside the request body and standard headers allows the backend to safely deduplicate duplicate retry requests, preventing double resource consumption.
**Prevention:** Always generate a unique client-side `idempotencyKey` for resource-creation POST requests and bind it to both the request payload and headers, combined with a defensive request timeout (e.g., 60 seconds) to ensure predictable and secure API transactions.
