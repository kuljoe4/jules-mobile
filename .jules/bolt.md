## 2026-07-24 - Algorithmic O(N^2) Over-rendering and Reference Stability Anti-pattern
**Learning:** In list-heavy React architectures (like `SessionList`), calculating item-specific relationships (like "drift" across all sessions) inside individual items leads to O(N^2) work on every single render. Moving aggregations to the parent level via `useMemo` reduces complexity to O(N) and keeps lookups constant-time O(1) inside items. Furthermore, wrapping a component with `React.memo` is completely bypassed if fallback props evaluate to a new reference on every render (such as `activitiesMap[s.id] || []` or inline closures like `onPress={() => onSelect(s)}`).
**Action:** Always pre-aggregate list statistics at the parent/store level. Use a custom `areEqual` comparator in `React.memo` to explicitly ignore recreated inline closures, and replace default inline empty object/array fallbacks (`|| []`) in prop mappings with module-level constants (e.g. `EMPTY_ARR = []`) to preserve reference stability and prevent unnecessary re-renders.

## 2026-07-25 - Excessive Object Serialization with Media Payloads Bottleneck
**Learning:** Using `JSON.stringify` on rich domain entities (like activities or sessions) to perform general string-matching/regex-lookup operations introduces a critical vulnerability when those objects contain nested, large base64-encoded media data (e.g., screenshots/videos). This results in massive CPU churn and huge memory allocations on every card render in lists.
**Action:** Avoid full-object stringification in nested lists or selectors. Instead, target explicit text properties directly (e.g. descriptions, titles, prompts) where links or keywords actually reside, and implement size-bounded caching maps (such as `PR_INFO_CACHE`) for expensive computed selectors.

## 2026-07-27 - Safe Reference-Stable Size Calculation Caching via WeakMap
**Learning:** Caching reference-stable size/complexity calculation results inside a recursive utility (like `getApproxBytes`) can drastically cut down rendering/diffing overhead from O(N * M) to O(N). However, arrays are prone to mutability and reference sharing, so caching them can yield stale results. Furthermore, `typeof null` resolves to `"object"` in JavaScript, meaning calling `WeakMap.has(val)` on a non-null object check without a strict `val !== null` guard will crash the app with a `TypeError`.
**Action:** Use a `WeakMap` to cache recursive byte size estimations, but restrict caching solely to non-array objects to prevent stale-data issues under mutation, and always explicitly guard `WeakMap` operations with `val !== null` to guarantee absolute runtime safety.

## 2026-07-28 - WeakMap Reference-Stable Activity-Level Performance Caching
**Learning:** Caching computed session properties like ahead commits and check statuses based on session keys combined with array lengths is highly vulnerable to stale content updates if activity details are updated in-place without changing array length. Utilizing a `WeakMap` keyed by individual reference-stable activity objects allows caching granular computed properties of activities (like regex check statuses and hash matching) with O(1) performance. This completely bypasses expensive regex executions and string allocations on re-renders, while maintaining absolute correctness and automatic garbage collection.
**Action:** For repeat list traversals computing aggregate status/stats, cache per-item results using a `WeakMap` keyed by the item objects themselves. This achieves complete correctness, avoids manual cache size checks, prevents memory leaks, and achieves significant speedups.

## 2026-07-29 - Activity-Level WeakMap Branch Extraction Optimization
**Learning:** Frequent loop traversals on activity arrays performing regex-based branch and compare/tree link extraction (e.g., within `getBranchInfo`) lead to O(N) execution overhead with nested string matching on every single UI render. Because activities are immutable and reference-stable objects, we can compute all regex-matched branch properties once in a single pass and cache them using a global `WeakMap`. This completely avoids CPU-intensive string processing and regex compilation/matching across successive renders.
**Action:** Always cache complex multi-regex extraction steps on immutable/reference-stable array items using a `WeakMap` cache. Doing so turns recursive and nested linear loops back into constant-time O(1) operations with zero garbage-collection or memory footprint penalty.
